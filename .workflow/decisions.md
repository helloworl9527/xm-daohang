## D-01 Web 应用形态（已定稿 @2026-08-08）
- **结论：方案① Next.js 全栈一体化 + 后台 worker 进程**（用户原文："就按1来"）。
  - Next.js 提供网页 UI 与 API；另起一个后台 worker 进程承载异步抓取、嵌入生成、定时重抓、Telegram bot；共用同一 PostgreSQL。
  - 非严格前后端物理分离；是"一体化应用 + 后台任务进程"。
- 被否决：严格前后端分离（独立后端 + SPA）——在"单人自部署、几百条"规模下，维护两套工程 + API 契约的收益不足以抵消运维成本。
- **重要：信息架构调整（用户补充，待细化确认）** —— 用户要求把网页拆成"两个不同网页"：
  - **前端（展示端）**：只负责展示已添加内容 + 提问检索；**提问框固定在页面底部正中**。
  - **后端（管理端）**：负责配置相关功能（含添加内容、库管理、模型配置、定时重抓、安全、TG、语言）。
  - **已确认（@2026-08-08）**：
    - 前端展示端 = **公开只读，不登录**；仅展示每日随机 3 条（去重轮换）+ 底部居中提问框。
    - 提问框 = **对公众开放，不登录**；返回全库命中；用户明确接受"库内容通过公开问答对外可见"（意图即公开可用）。
    - 公开提问加 **可配置次数限流**（单 IP + 全站每日总量；默认 20/日·IP、200/日·全站，管理端可改）。
    - 管理端 `/admin` = **仅用户名 + 密码登录（不启用 2FA，用户 @2026-08-08 明确要求去掉）** + 登录失败限流；承载添加/库管理/全部配置。2FA 列为后续可选增强。
    - 部署形态 = **同一 Next.js 应用的两个区域**（`/` 公开、`/admin` 受保护），一次部署。
  - 新增功能：F-11 每日 3 条轮换展示、F-12 公开提问限流；见 requirements.md v0.3。

## D-02 数据库与检索方案（已定稿）
- 结论：**PostgreSQL + pgvector**——单库同时承载结构化数据与向量语义检索；规模约几百条使用精确余弦扫描，不建 ANN 索引，部署与备份简单。
- 候选 B：Meilisearch（用户点名参考）——检索体验好、自部署方便，但主打关键词/前缀检索，语义/向量能力与结构化数据仍需另配库，等于多一个组件；在"几百条 + 需要语义关联"的场景属过度配置。
- 候选 C：SQLite + FTS/向量扩展——最轻，但公网 VPS 多进程/后台任务并发写与向量能力较受限。
- 定稿理由：语义关联检索（已确认）+ 关系数据一库解决，PG+pgvector 最契合且不过度；Meilisearch 的收益在本规模下不足以抵消多组件成本。更换嵌入模型按计划探测维度并版本化重建；规模/时延超过计划停止条件时才评估 HNSW。

## D-03 模型接入层（已定稿）
- 结论：抽象一层**OpenAI 兼容客户端**，对话模型与嵌入模型**各自独立配置**（baseURL + Key + 模型名），支持官方厂商 / 中转 / 本地 Ollama·vLLM。
- 依据：用户已确认"分别配置、以 OpenAI 兼容为主"。
- 安全：API Key 加密存储、不回显、日志脱敏（见 F-08）。

## D-04 Telegram bot 接入方式（已定稿）
- 结论：v1 使用 **long polling**，实现简单且无需新增公网回调；单 worker 持有 polling。
- 被否决：webhook 虽实时且适合公网 VPS，但需要额外回调路由、secret 校验与反向代理配置，在单机/单 worker v1 中收益不足。
- 失效条件：部署多个 worker 副本前必须改为 leader election 或 webhook，不得让多个实例同时 polling。
